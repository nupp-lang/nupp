## Summary

A worker call is typed from a protocol the entry module declares, so the
argument, the result, the operation name and the entry name are all checked
where the call is written. The handle is a structural type generated by a
comptime function from a string literal and a shape of operations; the literal
is what keeps two workers apart, since a comptime function cannot mint a
nominal type. The entry name stays an ordinary string argument rather than
becoming a resolved module reference, and the tie between that string and the
protocol is the alias the entry module exports.

## Goals

- Make a worker call read and check like an ordinary method call, including at
  the call site's argument list.
- Check the entry name at compile time, so a typo is a diagnostic rather than a
  spawn failure.
- Keep the share-nothing isolation intact: nothing here may cause the spawning
  state to load the entry module's code.
- Keep the spawned worker's cleanup obligation, so a typed handle is no easier
  to leak than today's untyped one.
- Give a worker pool and a non-blocking submit somewhere to live, rather than
  leaving every caller to build them over `call`.

## Non-goals

- Resolving a module name to a module type at the type level. That would remove
  the last redundancy from the call site, and it is deliberately out of scope;
  see [Alternatives considered](#alternatives-considered).
- Dynamic worker registration. Entries are fixed in the build target, and
  nothing in this proposal changes that.
- Making `nupp.workers` a job queue that outlives its process. Durability,
  remote workers and retry across a restart belong to
  [](nupp.io.process) and a broker, not here.
- Deciding transferability statically in full. Depth, cycles and repeated
  aliases stay dynamic, because a recursive type is a valid type that builds a
  cyclic value.

## Motivation

`nupp.workers` is the only part of Nupp that runs on a second core, and it is
the least typed part of the language. The request and reply are `any`, the
entry is a string the build resolves at run time, and the message shape exists
only inside a closure handed to `serve`. Every mistake that Nupp exists to
catch — a misspelled field, a changed reply shape, a wrong operation name — is
a run-time failure here.

The obvious answer is to derive the caller's type from the entry module, since
the build already knows every entry. It does not work as stated. The entry name
reaches the runtime as data, a `const` string parameter is not reifiable as a
value, and resolving a module name to a module type at the type level is
machinery Nupp does not have. What Nupp does have is enough: a comptime
function that builds a structural type, a literal type to carry the name, and a
`const` parameter that infers from the call argument, so one string serves as
both the runtime entry name and the compile-time check.

The remaining redundancy — the caller naming both the entry string and the
handle type — buys the isolation guarantee. A type-only `require` erases
completely, so naming the protocol costs the spawning state nothing at run
time.

## Overview and specification

### Syntax

The entry module declares its operations as a shape and exports a handle alias:

```nupp
local type Operations = {
    hash: function(job: Job): Answer,
    verify: function(job: Job, digest: uint64): boolean
}

export type Handle = workers.Handle<"jobs.hash", Operations>
```

### Worked example

```nupp
module jobs.hash

const workers = require("nupp.workers")
const data = require("nupp.data")

export type Job = {name: string, bytes: string}
export type Answer = {name: string, hash: uint64}

local type Operations = {
    hash: function(job: Job): Answer
}

export type Handle = workers.Handle<"jobs.hash", Operations>

export function main(self: workers.Self<Operations>): nil
    self:serve({
        hash = function(job: Job): Answer
            return {name = job.name, hash = data.fnv1a64(job.bytes)}
        end
    })
end
```

```nupp
const workers = require("nupp.workers")
const {type Handle} = require("jobs.hash")

local function hash(contents: string): uint64
    local hasher: Handle = workers.spawn("jobs.hash")

    return hasher:hash({name = "level1", bytes = contents}).hash
end
```

### Lowering

The type layer erases entirely. `workers.Handle` is a comptime application, so
neither it nor the operations shape appears in generated Lua, and a `require`
that only supplies types emits nothing. What remains is the call the untyped
surface already made, with the operation name added to the frame so `serve` can
dispatch on it.

### Handle identity

The generated handle is structural, because a comptime function constructs
types and never declarations. Typing the `entry` field as the string literal is
what discriminates: two handles over different entries have different `entry`
types and do not interconvert. This is weaker than nominality only in that a
second alias could declare the same name with different operations, which the
exported-alias convention is what prevents.

### Effects

An operation's declared signature is not the handle method's signature. A
worker call may park on a readiness source whatever the operation promises, so
the generated method is may-yield even where the operation is `nosuspend`.
Ownership does not survive the boundary either: values are copied, so an affine
parameter or result is refused when the handle type is generated.

### Errors

A failed operation raises in the caller, carrying the reply's message, which is
what `call` does today. The alternative — every operation returning a union
with a worker error — was rejected because it grows every signature and stops
the call reading like an ordinary call, which is the whole point.

### Entry lifecycle

An entry module exports `main(self)` rather than serving at load. This matters
for isolation rather than for style: a spawning state that imports the entry
module for a *value*, such as a record constructor, emits a real `require`, and
a module that served at load would then raise in the parent. With an exported
entry point, importing an entry module for its declarations is always safe.

### Pool

A pool is a second owned type over the same generated protocol, with `submit`
returning a ticket and `await` taking one. The request identifiers, the pending
set and the out-of-order reply routing this needs already exist to support
`call`; the pool contributes dispatch across workers and a waiting `submit`.

A pool may wait for queue capacity where a bare channel may not. Channels raise
instead of waiting so that producer backpressure cannot introduce a second wait
that deadlocks against the first; a pool owns both ends of its queues, so it
can wait without that risk. Under no suspension handler a pool of N behaves as
a pool of one, because each await blocks the thread.

Registration and de-registration are not new. `nupp.manage` moves a spawned
worker's obligation into a cell, and `nupp.managed.Group` adopts it, hands back
copyable aliases, and gives the owner back on removal. A pool is that pattern
specialised, not a new lifetime model. See [ownership.md](../type-system/ownership.md).

### Wire format

Messages are encoded from a schema built for the declared types rather than by
walking an unknown value. The walk that today rejects an unsendable value
before encoding becomes a compile-time check for everything it can decide, and
survives at run time only for types that may recurse.

The schema's compatibility fingerprint is the handshake between states. Both
sides compile from one payload, so a mismatch is a build property; the
fingerprint is what proves that rather than assuming it.

## Risks and assumptions

- **Structural messages accept an extra field.** Width subtyping means a
  misspelled field is accepted at the call and then dropped by the encoder. This
  is the price of table-literal call sites, and the transferability check is
  where it gets reported, since it already walks the declared type.
- **The exported alias is a convention, not a proof.** Nothing stops a second
  alias declaring the same entry name with different operations. Closing that
  needs the module projection this proposal declines to build.
- **Terminal naming is a prerequisite.** A generated handle cannot be given a
  cleanup obligation from outside `nupp.workers` until a function exported by a
  required module can be named as a const terminal. Intersecting with
  `nupp.Closeable` supplies ownership without that fix, but a nominal in the
  intersection swallows unknown-member lookup, which trades away the misspelled
  method diagnostic this proposal exists to add.
- **The entry lifecycle change breaks a documented pattern.** Code that calls
  `workers.current():serve(...)` at load stops working, and a diagnostic for an
  entry exporting no `main` is what makes that survivable.

## Alternatives considered

**Resolve the module name to a module type.** `spawn("jobs.hash")` would derive
its protocol from that module's declarations, removing the handle annotation
entirely. The build already knows every entry, and module checking already
publishes exported signatures before bodies are checked, so the information is
there. It lost on cost rather than on principle: it is a new type-level
operator projecting a statically named module, and everything else here works
without it. It stays available later, and would make the exported alias
optional rather than obsolete.

**A witness interface carrying associated types.** An `Entry<const Name>`
interface with `associated type Input` and `Output`, answered by a record in
the entry module and consumed through a `Handle<N, E is Entry<N>>` generic.
This checks, and it makes the handle nominal. It lost to the comptime function
on weight: about twelve lines of protocol declaration per worker against one,
for a nominality the literal `entry` field already supplies.

**Nominal message records.** Records catch an unknown field at construction and
carry derives and reflection for free, including `derive.Serde`, which
structural shapes cannot use. They lost because `new Job(...)` at every call
site defeats the goal; the cost is paid instead by building the serde schema
from a shape descriptor.

**A result union per operation.** Rejected under [Errors](#errors).

**Typed one-shot spawn only, no pool.** Leaving pools to callers keeps the
surface small, but every caller then rebuilds dispatch, ticketing and
backpressure over `call`, and the backpressure question in particular has one
right answer that depends on owning both ends of the queue.

## FAQ

### Why is the entry name written twice?

It is written once as a string and once inside the handle type the entry module
exports, and the two are checked against each other. Collapsing them needs the
module projection above. Writing the string alone would leave the operations
unknown; writing the type alone would leave the runtime without the name, since
a `const` parameter has no runtime form.

### Can a worker still be untyped?

Yes. The untyped `call` and `serve` remain for a worker whose protocol is not
worth declaring, and for one-way `send` and `receive` messages, which are a
separate protocol in the other direction.

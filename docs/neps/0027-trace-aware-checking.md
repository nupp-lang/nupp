## Summary

One trace-reason engine combines facts from checked source, generated bytecode,
the pinned recorder, and optional observed trace events, and is reached through
three surfaces: a static bytecode check that reports unconditional recorder
blockers and exits nonzero, an annotation that makes those blockers
non-suppressible contract errors, and a run-time report of what the recorder
actually refused. Ordinary check, build, and run inject nothing.

[JIT trace checking](../guides/jit-trace-checking.md) documents the surface.

## Goals

- Answer a question no other tool answers: whether a loop can be recorded at
  all, rather than how long it took.
- Give the same answer on any machine, without a quiet one.
- Make claims that are exactly true, and refuse to make the tempting one.

## Non-goals

- Forking the runtime, parsing its textual output, or maintaining an independent
  model of its optimizer.
- Injecting counters, probes, loop callbacks, or hidden instrumentation into
  ordinary builds.
- Claiming a function is hot, will be called, will form exactly one trace, or
  will stay compiled for every input.
- A cost model, instruction scheduler, register-pressure oracle, or benchmark
  replacement.
- Making runtime profile results part of whether source checks.

## Motivation

### Falling off a trace is invisible to every other tool

A loop that aborts recording runs interpreted however hot it gets. A sampling
profiler shows it as slow without saying why; a benchmark shows a number without
saying what changed. The fact is structural — it is a property of the emitted
bytecode and the recorder — so it can be read rather than measured, which means
it needs no quiet machine and gives the same answer every run.

### The tempting claim is the false one

The claim a user wants is "this function will run as machine code". It cannot be
made: a loop may never run, may stay cold, may take runtime types the recorder
cannot specialize, or may side-exit for input-dependent reasons.

## Overview and specification

### Six verdicts, each exactly as strong as its evidence

```text
 Verdict               Meaning
 ────────────────────  ────────────────────────────────────────────────────
 Unconditional         Recording aborts whenever the pinned recorder
   blocker             reaches that operation.
 Must-reach blocker    Unconditional on every repeatable path through the
                       named loop, so that loop cannot complete a root trace.
 May-reach blocker     Unconditional once reached, on only some paths.
 Conditional risk      Depends on runtime types, call targets, shapes,
                       limits, or target details. Advisory.
 Observed abort        Came from the VM hook in this execution.
 Expected stop         Ordinary completion, recursion, or loop exit.
                       Informational, not a failure.
```

The value of the design is in this table. A single "will it compile?" answer
would have to be wrong somewhere; six verdicts each carry exactly the confidence
their evidence supports, and the last one exists so ordinary behaviour is not
reported as a problem.

### One reason registry, four fact sources

Static checking reads compiler facts and emitted bytecode. Runtime observation
is opt-in, uses the existing VM trace hook, and costs only while a trace session
is active. All of it normalizes through the same registry, so a statically
predicted blocker and an observed abort are the same identity.

**Raw recorder strings are not retained as diagnostic identities or public API.**
They are unstable, and building a public surface on them would tie diagnostics to
an implementation detail of a component Nupp does not own.

### Ordinary builds pay nothing

No counters, edge probes, loop callbacks, hidden zone pushes, or alternate
bytecode in ordinary or trace-checked builds. Attribution zones remain optional
and are not a prerequisite for a verdict.

### Two execution contracts stay separate

The trace annotation does not imply the ahead-of-time one, and they do not share
eligibility catalogs. They are mutually exclusive execution contracts, and
merging their vocabularies would produce a diagnostic that means one thing in
one context and something else in the other.

### Checking is independent of running

The same source and target check identically without running the program. A
profile can inform a person; it does not change whether source is accepted.

## Risks and assumptions

- **The verdicts are only as good as the pinned recorder model.** They are
  claims about a specific runtime version. A recorder change can turn a correct
  verdict into a wrong one with no signal.
- **"Unconditional blocker" is a strong claim from static reading.** It is the
  one users will act on, and being wrong about it means rewriting code for no
  reason.
- **Six verdicts is a lot to teach.** The distinction between must-reach and
  may-reach is exactly right and is not obvious, and users under time pressure
  will read every verdict as "problem".
- **Advisory verdicts risk being tuned toward.** A conditional risk depends on
  things the compiler cannot see, and rewriting to silence one without a
  benchmark is how a codebase acquires unmotivated contortions.

## Alternatives considered

**Parsing the runtime's textual diagnostic output.** Rejected: the format is
unstable and undocumented, and it would make Nupp's diagnostics a function of
another project's logging.

**Forking the runtime** to get a supported query interface. Rejected as a
maintenance commitment far larger than the feature.

**Maintaining an independent model of the optimizer.** Rejected: it would be a
second implementation that drifts, and the answers would be confidently wrong
rather than absent.

**Injecting counters and probes** to get precise data. Rejected: instrumentation
changes what is recorded, so the measurement perturbs the thing being measured —
and it would put a cost on ordinary builds.

**One verdict instead of six.** Rejected: any single answer overclaims for some
evidence and underclaims for other, and the useful distinctions — must-reach
versus may-reach, predicted versus observed — are exactly the ones a single
answer erases.

**Reporting every side exit.** Rejected: ordinary trace stops are not failures,
and a tool that reports them trains people to ignore it.

**Making profile results affect checking.** Rejected: it would make acceptance
depend on having run the program, on a particular machine, with particular
input.

## FAQ

**Does this tell me my function will be fast?** No. It tells you whether the
recorder can compile it, which is a different and narrower claim.

**Why does it need no quiet machine?** Because it reads bytecode rather than
timing anything, so the answer is the same every run.

**What does ordinary `nupp build` pay?** Nothing. No instrumentation is injected
in any build.

**Can I use the trace annotation together with ahead-of-time compilation?** No.
They are mutually exclusive execution contracts.

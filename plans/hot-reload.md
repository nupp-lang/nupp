# Hot reload: a design and implementation plan

Status: proposed. Nupp already has incremental per-file checking and a runtime
loader, but generated functions have ordinary Lua identity and a module can only
be loaded as a whole. This plan adds a development-only patchable target without
changing normal generated Lua.

## Decision

Nupp will support hot reload as a distinct compilation target with two halves:

- a persistent compiler session checks changes and emits inert patch chunks;
- a small runtime stages those chunks and commits a complete generation when
  the host says it is safe.

The compiler owns function identity, compatibility, capture preservation, patch
format and diagnostics. The host owns the event loop and the commit boundary.
`nupp run --watch` can supply both for an ordinary program; an embedding host
such as tecs can drive the same interfaces and commit during its own ingress
phase.

Watch-generated functions whose identity may outlive their defining module are
stable trampolines. A trampoline is installed once and dispatches through a
compiler-owned slot whose implementation changes at commit. Loading a patch
does not rerun module top level, replace `package.loaded`, rebuild record tables,
or mutate a live slot. It creates candidate implementations and a manifest;
staging proves that the whole patch is compatible before commit changes any
slot.

Normal compilation is not a degenerate form of watch compilation. When watch
mode is absent, the current generator path and its output remain byte-identical:
ordinary functions, direct calls, no slots, no registry, no polling, no reload
runtime and no per-frame condition.

## Goals

1. A valid function-body edit becomes visible to future calls without restarting
   the process or rebuilding application state.
2. Existing function values, module tables, record tables and captured mutable
   variables retain their identity across a commit.
3. A syntax, type, generation or compatibility error leaves the last good
   generation running and reports why the change did not land.
4. A multi-function patch is atomic: every replacement in one generation lands,
   or none does.
5. A host can prepare patches whenever source changes and commit them at a safe
   point of its choosing. Nupp does not require ownership of the host loop.
6. Suspended or currently executing calls finish on the implementation they
   entered; later calls enter the committed implementation.
7. Unwatched builds retain current generated bytes, runtime dependencies,
   startup behavior, JIT behavior and performance.
8. The first release is useful for tecs system, predicate, observer and callback
   bodies when those callbacks are named functions.

## Non-goals

- Replacing the Lua VM, serializing a world, or recreating application state.
- Rewinding or transplanting a currently executing Lua stack frame into a new
  function body.
- Silently rerunning module initialization, plugin registration, resource
  creation or arbitrary top-level effects.
- Migrating changed component, record, struct, cdata or native layouts in the
  first release.
- Adding, removing or reordering tecs systems through a body patch. A later
  lifecycle protocol may support structural changes explicitly.
- Making every anonymous closure reloadable in the first milestone. Stable
  anonymous source-site identity is planned after named functions prove the
  patch ABI.
- Building a scheduler into Nupp. The existing suspension API and a host's
  scheduler remain separate from hot reload.
- Paying a runtime branch, indirection or bundled-code cost in a normal build.

## User and host surfaces

### Standalone command

Add watch to the command that already owns a standalone program's lifetime:

```text
nupp run --watch [--strict] [-O<n>] <file> [args...]
```

The command performs the initial watch build, runs the entry chunk, observes
project source files, prints diagnostics for rejected generations and commits a
valid generation between host turns. A program that never returns control to a
polling or suspension boundary cannot be made cooperatively reloadable; document
that limitation rather than adding preemption.

The first implementation may expose a lower-level compiler command before the
standalone loop is complete:

```text
nupp watch --patch-out <channel> <entry>
```

The exact transport is intentionally outside the patch schema. A development
host may embed the compiler, supervise it as a child process, or exchange framed
patch chunks over an existing control channel.

### Compiler session

Add a host-neutral compiler-side object, conceptually:

```nupp
record hotreload.Session
    diskChanged: function(self: hotreload.Session, path: string, changeType: integer)
    prepare: function(self: hotreload.Session, paths: {string}): hotreload.Result
    persist: function(self: hotreload.Session)
end
```

`Session` owns one `incremental.Inc`. `diskChanged` forwards invalidation to the
existing query graph. `prepare` checks the affected source closure, compares its
public interface with the running generation, generates candidate bodies and
answers one of:

```text
PreparedPatch   complete, loadable patch bytes plus manifest
Diagnostics     syntax/type/generation failures; old generation remains valid
RestartRequired well-typed change outside the patchable contract
NoChange        no emitted implementation changed
```

Do not route watch rebuilds through `compile.module`, which creates a fresh
parse/check/generate pipeline for one file. Reuse `incremental.Inc` so a body
edit rechecks its file while unchanged exported interfaces cut off dependent
work.

### Runtime

Add a small development runtime with an embedding surface equivalent to:

```nupp
local hot = require("nupp.hotreload")

const prepared, stageError = hot.stage(patchChunk)
if prepared then
    -- The host chooses this boundary.
    hot.commit(prepared)
end
```

`stage` loads an inert patch chunk, checks its schema and running-generation
identity, resolves every stable function and capture, and allocates everything
needed for commit. It must not alter a live slot. `commit` performs only bounded
runtime work: swap the prepared slot targets, publish the generation number and
invalidate stale JIT traces.

Only one prepared successor to a running generation may commit. A patch declares
its base generation; staging or committing it after another patch landed reports
a stale-generation result and asks the compiler for a replacement.

## Watch code generation

### Stable slots and trampolines

For a named function whose value escapes into a module table, record method,
callback registry or another long-lived value, watch emission is conceptually:

```lua
local __slot = __hot.define("game.systems/movement", metadata, function(world, dt)
   -- initial implementation
end)

local function movement(...)
   return __slot.impl(...)
end
```

The trampoline is the public function value and never changes. Only the slot's
`impl` changes. Preserve Lua's argument and multiple-return behavior; the
trampoline must be a tail call wherever LuaJIT permits it. Function diagnostics
and stack traces should still name the Nupp source path and line rather than a
runtime helper.

The simplest first generator may slot every named runtime function in a watch
module. A later escape analysis may limit trampolines to functions whose
identity crosses a reload boundary, but that optimization must not precede a
correct identity model. Private helpers compiled wholly inside a replacement
body may remain direct functions when no old value can retain them.

Methods currently emitted into record and struct method tables receive the same
stable treatment. A reload patches their slots; it does not recreate an FFI
metatype or replace its `__index` table.

### Stable IDs

Version one assigns IDs to named declarations from semantic structure, not byte
offsets alone:

```text
schema version / canonical module name / lexical owner path / declaration kind / name
```

Two overload-lowered runtime members include their final runtime member names.
Compiler-generated helpers include the authored declaration that owns them and
a stable role name, never a temporary counter.

An insertion above a declaration must not change its ID. Duplicate local names
in different lexical blocks remain distinct through the owner path. Moving a
function between owners is a structural change and requires restart.

Anonymous functions need a later source-site reconciliation algorithm. The
finished tecs experience requires it because inline `run = function() ... end`
callbacks are idiomatic. That milestone should match sites between the last good
checked tree and the candidate tree using lexical owner, syntactic role and
structural neighborhood. Line and byte offsets may break ties but cannot be the
identity. An explicit stable-ID annotation is a fallback for inherently
ambiguous sites, not the default programming model.

### Capture inventory and preservation

Checking must attach a complete free-variable inventory to every reloadable
function. The existing `takenCaptures` and borrowed-capture data describe
ownership-specific explicit captures; they are not a complete list of ordinary
Lua upvalues such as a tecs `app`, query or resource local.

Each capture manifest entry contains:

```text
stable binding ID
authored name for diagnostics
type/interface fingerprint
ownership or borrow mode where applicable
new closure upvalue index
```

The initial watch chunk registers a handle to every persistent lexical cell a
future implementation may capture. A patch implementation is constructed with
placeholder upvalues, and staging joins each placeholder to the existing cell
with `debug.upvaluejoin`. Joining rather than copying preserves mutation shared
between closures.

Version one requires the same capture IDs, types and modes. Adding, removing or
retargeting a capture is `RestartRequired`. This restriction also avoids the
case where no running closure exposes a newly captured lexical cell. A later
watch lowering may anchor every module binding or represent persistent bindings
as explicit cells, at which point compatible capture-set growth can be allowed.

Owned and borrowed captures keep their language rules. Hot reload must not clone
an owner, extend a borrow, run a cleanup, or make an uncalled replacement closure
responsible for a second cleanup. Replacement implementations borrow the same
already-established lexical cells; the stable trampoline retains the original
lifetime.

### Patch chunks

A patch chunk is data plus newly compiled closures. It has no authored top-level
execution:

```lua
return {
   schema = 1,
   project = "<project fingerprint>",
   baseGeneration = 7,
   generation = 8,
   modules = {
      {
         name = "game.systems",
         interface = "<interface fingerprint>",
         source = "src/game/systems.nupp",
         functions = {
            {
               id = "game.systems/movement",
               signature = "<callable fingerprint>",
               captures = { ... },
               implementation = function(world, dt) ... end,
            },
         },
      },
   },
}
```

The schema is versioned and validated as untrusted input. Reject duplicate IDs,
unknown fields that change semantics, missing functions, malformed capture
indices, a different project, compiler/runtime schema mismatch, or a base other
than the running generation. Do not expose mutable runtime slot tables to a
patch chunk.

Patch chunks preserve the generator's source-line invariant. Generated wrapper
or manifest plumbing belongs on existing lines or before the first authored line
without shifting it; replacement function bodies retain their `@source.nupp`
chunk name.

## Compatibility contract

The compiler, not the runtime, gives the useful authored diagnostic. It compares
the last committed manifest with the checked candidate before emitting a patch.
The runtime repeats security- and correctness-critical checks because a patch
may cross a process boundary.

Version one accepts:

- edits inside the bodies of an existing reloadable function or method;
- literal and control-flow changes contained in those bodies;
- changes to private functions created wholly inside a replaced body;
- compatible optimizer-output changes caused by those edits.

Version one requires restart for:

- a changed exported module interface or callable signature;
- addition, removal, rename or movement of a stable declaration;
- a changed capture set, capture type or ownership/borrow mode;
- changed top-level executable statements or initializers;
- changed record, struct, cdef, metatype, component or native layout;
- a changed constructor, derive or materialization result that affects runtime
  identity or initialization;
- a changed implicit runtime feature/provider set;
- addition or removal of a module from the running source set.

The result should distinguish a broken edit from a valid edit requiring restart:

```text
NUPPxxxx error: `movement` now captures `acceleration`
  help: restart the program to apply this structural change

nupp: generation 12 rejected; generation 11 is still running
```

Reserve a compact diagnostic family for hot-reload incompatibilities and make
each code available through `nupp explain`. Related locations point to the old
and candidate declarations when both are available.

## Transaction and execution semantics

Staging performs every fallible operation: loading candidate closures, schema
validation, ID lookup, callable and capture comparison, upvalue joining and
allocation of the final target vector. Commit must not call authored code.

Commit order is:

1. verify the prepared patch still names the running base generation;
2. replace every target in the prepared vector;
3. publish the new generation number;
4. invalidate JIT state;
5. release references held only for rollback/staging.

Lua execution is single-threaded at the commit boundary, so readers cannot
observe an intermediate slot swap. No user callback, finalizer or allocation
with an authored metamethod may run between the first slot swap and generation
publication. If that cannot be proven for a data structure, construct the new
generation table before commit and swap one registry root instead.

Start with a full `jit.flush()` after a successful commit. It is watch-only and
therefore favors correctness over retained warm traces. Later, prove and test a
narrower invalidation strategy before adopting it.

A call already inside an old implementation retains that closure on its stack
and completes there. A suspended coroutine also resumes the old implementation.
The next invocation through a stable trampoline reads the new target. Retain old
implementations while a stack may reference them; Lua's ordinary reachability
does this without an explicit generation refcount.

## Module and state semantics

The initial watch build executes modules normally once. It registers slots and
persistent binding handles as part of that execution. Later patches do not:

- clear or replace `package.loaded[name]`;
- rerun a module chunk;
- reconstruct its returned table;
- rerun constructors, registrations or top-level calls;
- repeat `ffi.cdef` or `ffi.metatype`;
- rewrite non-function module fields.

This is intentionally body reload rather than module reload. Existing entities,
resources, queries and closures keep their state because the patch retains their
tables and lexical cells.

A later lifecycle layer may add explicit hooks:

```nupp
@reload
function module.onReload(previous: ModuleVersion, next: ModuleVersion): nil
```

Such a hook needs its own transactional and failure semantics and is not part of
the first patch ABI. It must never arise from silently reexecuting top level.

## tecs composition

Nupp does not need to compile the tecs engine. A Nupp-authored game needs Nupp
declaration modules for tecs's public Lua surface, while the engine remains its
normal Teal/Lua build.

The intended development flow is:

```text
source change
  -> Nupp incremental session checks and generates an inert patch
  -> patch is loaded and staged in the game VM
  -> tecs waits until no logical update is stalled and no batch is open
  -> tecs commits at fresh ingress
  -> the same world runs future systems through the new implementations
```

Tecs supplies only an adapter that:

1. reports source changes to an embedded Nupp session or receives prepared
   patches from a Nupp sidecar;
2. retains the newest successfully staged patch;
3. invokes `hot.commit` at its established safe ingress boundary;
4. reports committed, rejected and restart-required results through its normal
   development diagnostics.

Nupp should not import `tecs`, know about systems or poll the tecs watcher from a
generated module. The same runtime interface must work in another game loop,
server or GUI host.

Named functions are the initial ergonomic constraint:

```nupp
local function movement(world: tecs.World, dt: number): nil
   -- body may be patched
end

world:addSystem({run = movement})
```

The `world:addSystem` call runs once. The pipeline retains the stable `movement`
trampoline. The anonymous-source-site milestone later makes inline system
closures behave the same way.

Tecs API declarations are a separate integration deliverable. Generate or
maintain `.d.nupp` declarations for the application, world, system, query,
component, resource, event and sequence surfaces used by Nupp game modules.
Their version must participate in the project/interface fingerprint so a tecs
API change cannot accept a patch checked against different declarations.

## Zero-cost normal builds

Hot reload follows the same separation already used for coverage: the request
is absent in ordinary settings, and only the alternate generator mode allocates
metadata or emits helpers.

With watch disabled:

- `gen.generate` takes the current path and emits the same bytes;
- cache keys and artifacts stay in the ordinary namespace;
- functions and methods retain current direct Lua emission;
- no `nupp.hotreload` import or slot manifest is generated;
- no compiler, watcher or patch schema is bundled into an application;
- no runtime registry is created;
- no poll or conditional is added to a host frame;
- no `debug.upvaluejoin` or `jit.flush` is reached.

The Nupp compiler binary may grow, and selecting a generator mode is allowed to
cost compiler work only in watch mode. "Zero cost" here is a claim about normal
generated programs and their artifacts, not the size of the development tool.

Protect the claim with byte-for-byte golden tests over representative modules,
including functions, methods, captures, records, structs and optimized output.
`nupp fixpoint` must remain byte-identical.

## Implementation milestones

### H0: Freeze semantics and fingerprints

- Define the patch schema, generation rules and compatibility matrix.
- Add stable callable, lexical owner and captured-binding identities to checked
  results without changing ordinary generation.
- Inventory every runtime function form emitted by `gen`: named statements,
  function expressions, short functions, inline record methods, struct methods,
  constructors, derived functions and compiler-generated helpers.
- Add checker tests proving stable IDs survive body edits and preceding-line
  insertions, and differ across lexical owners.
- Decide which generated forms are patchable in H1 and diagnose the rest as
  restart-required.

Exit gate: two checked generations can be compared deterministically without
loading either one.

### H1: Named-function watch generation

- Add an explicit watch-generation request beside the existing coverage request.
- Emit initial stable slots and trampolines for named functions and methods.
- Emit a manifest containing IDs, callable fingerprints and complete capture
  inventories.
- Add the small runtime registry and initial-definition API.
- Preserve source line attribution and tail/multiple-return behavior.
- Keep normal output byte-identical and add direct assertions for that property.

Exit gate: retaining a function value across a synthetic replacement calls the
new body while ordinary builds still emit today's direct function.

### H2: Patch generation and capture rebinding

- Build a persistent hot-reload compiler session over `incremental.Inc`.
- Compare the candidate against the last committed manifest.
- Emit inert patch chunks containing changed named implementations only.
- Implement full ordinary-free-variable capture analysis.
- Stage replacements and join their upvalues to existing lexical cells.
- Reject capture and interface changes with authored diagnostics.

Exit gate: a captured mutable value retains identity across several body
patches; syntax/type/incompatibility failures leave the old body callable.

### H3: Transactional host API and JIT correctness

- Separate `stage` from `commit` and make patches base-generation-specific.
- Prove commit cannot invoke authored code or expose a partial target vector.
- Flush JIT state after commit.
- Test calls active during commit and coroutines suspended in an old body.
- Expose structured results suitable for CLIs and embedding hosts.

Exit gate: a multi-function patch either changes every future dispatch or none,
and stale/out-of-order patches cannot land.

### H4: Standalone watch command

- Add the watch option and file-change source.
- Reuse one incremental session for the process lifetime.
- Debounce or settle writes so editors that replace files do not create noisy
  transient generations.
- Keep the last good program running while printing current diagnostics.
- Define cooperative polling behavior and document programs that monopolize the
  VM.
- Add CLI JSON records for host tooling if the existing command-output model
  requires them.

Exit gate: a standalone fixture can be edited repeatedly, recover from a broken
edit and apply the next valid edit without restarting.

### H5: tecs adapter and declarations

- Publish or generate the Nupp declarations needed by a small tecs game.
- Add a tecs development adapter using the host-neutral stage/commit API.
- Commit only at fresh ingress, never during a stalled logical update or open
  batch.
- Exercise systems, `runIf`, observer/event callbacks and record methods.
- Verify the same world, entities, resources and queries survive each patch.
- Verify a crash-safe path can stage a correction and clear a recoverable game
  crash without committing inside an unsafe stalled update.

Exit gate: a running tecs example changes system behavior after a save without
re-registering systems or rebuilding the world.

### H6: Anonymous escaping closures

- Reconcile anonymous function sites across successive checked trees.
- Slot closures whose values escape into long-lived tables or calls.
- Preserve their captured cells and diagnose ambiguous matching.
- Cover inline tecs system and callback literals.
- Add an explicit stable-site annotation only if real ambiguous cases cannot be
  matched honestly.

Exit gate: the idiomatic inline `run = function() ... end` tecs form reloads
through ordinary body edits and preceding-line insertions.

### H7: Controlled expansion

Measure actual use before choosing among:

- compatible capture-set growth through anchored module cells;
- changeable immutable module constants;
- finer-grained JIT invalidation;
- explicit reload lifecycle/migration hooks;
- structural tecs system replacement;
- worker-generation policy and multi-VM patch distribution;
- native-code restart coordination.

None of these may weaken H0-H6 compatibility diagnostics into best-effort
mutation.

## Verification matrix

### Compiler

- Stable IDs are deterministic across processes and compiler fixpoint rebuilds.
- Body-only edits do not invalidate unchanged dependent interfaces.
- Normal and watch artifacts occupy distinct cache identities.
- Patch output is deterministic for identical base and candidate generations.
- Normal generated Lua remains byte-identical at every optimization level.
- Source paths and lines in replacement stack traces point to authored Nupp.

### Runtime identity

- A retained function compares equal to itself before and after reload.
- A module table and record method table retain identity.
- Mutable captured locals are shared by old sibling closures and the new body.
- Recursive and mutually recursive functions dispatch according to the declared
  generation semantics.
- Nil and multiple returns pass through trampolines unchanged.
- Errors preserve the authored source location.

### Failure and transaction behavior

- Syntax, type and generation errors leave the running generation untouched.
- An incompatible signature, capture, layout or top-level change requests
  restart and does not partially land.
- A malformed, foreign, stale or duplicate-ID patch is rejected by the runtime.
- Failure while staging the last function in a patch changes no earlier slot.
- Two prepared successors of one base cannot both commit.

### LuaJIT and execution

- A function traced before reload executes the new body after commit.
- A hot loop does not retain an inlined old implementation after JIT flush.
- A call already executing finishes on its old implementation.
- A suspended coroutine resumes the old implementation and later calls use the
  new one.
- Repeated generations release unreferenced old closures and manifests.

### tecs

- Commit occurs only at safe ingress.
- One logical update never mixes generations through ordinary system dispatch.
- Existing world, entity, query, resource and system registration identities
  survive.
- A broken edit does not stop the last good generation.
- Normal non-watch tecs packaging contains no Nupp hot runtime or compiler.

## Repository work

Expected Nupp touch points, refined during H0:

- `src/nupp/compiler/check/`: assign callable and binding identities and record
  the complete free-variable inventory.
- `src/nupp/compiler/gen.nupp`: add isolated initial-watch and patch emission.
- `src/nupp/compiler/incremental.nupp`: expose generation inputs and comparison
  data through a persistent session without weakening current cache cutoffs.
- `src/nupp/compiler/cli/compile.nupp`: carry an explicit watch request while
  keeping ordinary settings unchanged.
- `src/nupp/compiler/cli/run.nupp`: standalone watch lifecycle after the
  compiler/runtime primitives exist.
- `src/nupp/hotreload.nupp` or an equivalent runtime namespace: stable registry,
  schema validation, staging and commit.
- `src/nupp/compiler/decls/`: declare any LuaJIT debug/JIT functions the compiler
  runtime uses rather than reaching them through `any`.
- `tests/`: unit tests for IDs, compatibility, generation and runtime identity;
  process fixtures for watch recovery; acceptance coverage for tecs.
- `docs/`: command, embedding contract, accepted edits, restart-required edits,
  execution semantics and the zero-cost guarantee.

The tecs adapter and public declarations belong in the tecs repository. Nupp's
acceptance fixtures may carry a minimal fake host or pinned test fixture, but
must not make the compiler depend on tecs.

## Risks and decisions to validate in H0

1. **Upvalue names and indices.** Generated lowering can introduce or reorder
   Lua upvalues. The manifest must use compiler-assigned binding IDs and emitted
   indices; runtime `debug.getupvalue` names are validation aids, not identity.
2. **Optimizer interaction.** Optimization may inline, eliminate or synthesize
   functions. Watch mode either constrains passes that erase patch boundaries or
   records a stable mapping through them. A pass may not make a named reloadable
   function disappear without an equivalent stable slot.
3. **Atomic root swap versus slot vector.** Sequential slot assignments are
   safe only while no Lua code can run. Prefer one generation-table root swap if
   finalizers, hooks or allocation make that proof fragile.
4. **Recursive calls.** Decide whether self-recursion in an old activation stays
   on the old implementation or traverses the stable slot into the new one after
   commit. The least surprising rule is generation consistency for an active
   call, but it may require the implementation to close over itself rather than
   call the public trampoline. Specify and test one rule before H1.
5. **Compiler placement.** An embedded compiler is simpler initially; a sidecar
   keeps compiler code and memory out of the game VM. Keep the patch and host
   interfaces transport-neutral so this remains a deployment choice.
6. **Security boundary.** A development host may receive patch bytes from
   another process. Treat schema data as untrusted, but acknowledge that loading
   Lua code is code execution and bind any transport to the local development
   session rather than advertising a network service.
7. **Watch source.** Native file watching is not required for the semantic core.
   Begin with a settled polling source or the host's existing watcher; do not
   couple patch correctness to one platform watcher backend.

## Completion criteria

Hot reload is complete for its first supported surface when all of the following
are true:

- a documented standalone or embedding workflow applies repeated named-function
  body edits in one process;
- state and retained function identity survive those edits;
- rejected generations never disturb the last good one;
- commit is atomic and host-controlled;
- LuaJIT cannot continue executing a stale trace on a future dispatch;
- a tecs acceptance example patches system behavior at safe ingress without
  rebuilding its world;
- normal generated output is byte-identical and contains no watch machinery;
- the accepted/restart-required matrix and active-call semantics are documented
  and enforced by tests rather than convention.
